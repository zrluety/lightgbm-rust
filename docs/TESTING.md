# Testing

All commands run from the repository root. Test reports are written to `tests/report/`. `summary.md` there is generated by script; never edit it by hand.

## Environment

- Rust toolchain from `rust-toolchain.toml`, plus Python 3.12 managed by `uv`.
- `uv sync --python 3.12` installs the dev group, which includes the reference engine `lightgbm==4.7.0` (PyPI wheel), pytest, pandas, scikit-learn, scipy, matplotlib, and the `graphviz` Python package.
- The tree-plotting tests also need Graphviz's `dot` executable on `PATH` (`apt-get install graphviz` on Ubuntu). Without it, upstream's `test_plot_tree` and `test_create_tree_digraph` fail when rendering.
- The reference engine is used **only** by `tests/differential`, `examples/train_binary.py`, and `benches/bench_vs_upstream.py`. The upstream test runner never imports it; it asserts that `lightgbm` resolves to `lightgbm_rust`.
- `uv sync` removes the editable `lightgbm_rust` install. After it, re-run `maturin develop` and use `uv run --no-sync`.

### Where this pass was verified

The results in `tests/report/summary.md` were produced on **WSL 2 Ubuntu (x86_64, Python 3.12.14)** on a Windows 11 host. Native Windows builds are expected to work (the code has no platform-specific parts) but have not been verified on this machine; the user chose WSL as the build environment. `scripts/wsl-dev.sh` sets up that environment:

- it keeps the cargo target directory (`~/lgbm-target`) and the virtualenv (`~/lgbm-venv`) on the Linux filesystem, which is much faster than `/mnt/c`;
- it puts `~/.cargo/bin` and `~/.local/bin` (uv) on `PATH`;
- it then runs its arguments.

From PowerShell:

```powershell
wsl -d Ubuntu -- bash -lc "cd /mnt/c/<path>/lightgbm-rust && bash scripts/wsl-dev.sh <command>"
```

PowerShell expands `$` inside double quotes, so put anything non-trivial in a script file rather than inline.

## Commands

| step | command |
|---|---|
| Rust unit, ported C++, and end-to-end tests | `cargo test -p lgbm-core 2>&1 \| tee tests/report/cargo_test.txt` |
| build and install the Python package | `uv run --no-sync maturin develop --release` |
| Python API tests | `uv run --no-sync pytest tests/python -p no:cacheprovider` |
| differential tests vs LightGBM 4.7.0 | `uv run --no-sync pytest tests/differential -p no:cacheprovider` |
| upstream Python suite, through the shim | `uv run --no-sync python tests/upstream_runner/run.py` |
| benchmark: 6 tasks (4 dense, 2 scipy CSR) × threads {1, 4, 8, all}, time and peak memory, each run in a fresh process | `uv run --no-sync python benches/bench_vs_upstream.py` |
| Rust micro-benchmark (criterion) | `cargo bench -p lgbm-core` |
| end-to-end example | `uv run --no-sync python examples/train_binary.py` |
| regenerate the report | `uv run --no-sync python tests/report/make_summary.py` |

`tests/upstream_runner/run.py` regenerates `summary.md` itself. Run the other steps first so their inputs are current.

## What each layer checks

### Rust tests (`crates/lgbm-core`)
- **Unit tests** cover each module: config/alias parsing, binning, histograms, split finding, objectives (finite-difference gradient and Hessian checks), metrics, and model text IO.
- **Ported upstream C++ tests** carry a `// upstream: tests/cpp_tests/<file>.cpp TEST(<suite>, <name>)` comment. `make_summary.py` scans for these comments to build the traceability table, so a port without the comment is not counted.
- **`tests/end_to_end.rs`** trains, saves, reloads, and predicts with no Python involved.

### Differential tests (`tests/differential`)
- **Engines.** Both engines are trained on the same data and parameters. The default setup is `deterministic=True`, `force_row_wise=True`, and `num_threads=1`; `test_multithread` uses 4 threads.
- **Bins.** Bin assignments are compared through `Dataset._dump_text`, and for cases with `max_bin_by_feature` or `forcedbins_filename` also its `max_bin_by_feature` and `forced_bins` lines. The forced-bin JSON files the cases use are in `tests/differential/data/`.
- **CEGB.** The `cegb_*` cases include bagging and GOSS in upstream's subset mode, where the bag size changes every tree and the lazy-penalty bitset positions depend on it. `test_cegb_changes_trees` checks that each case's upstream trees differ from the same case without CEGB (except `cegb_tradeoff_only`, which only turns CEGB on).
- **Forced splits.** The `fs_*` cases read their JSON trees from `tests/differential/data/forced_splits_*.json`. Several of them force a split on a leaf whose histogram of the forced feature was not built in that tree. That happens when the leaf was not split because of `max_depth` or `min_data_in_leaf`, when the parent could not split on the feature, or when the feature is outside the by-tree sample. Upstream then reads whatever an earlier build left in the leaf's histogram-pool slot, and these cases check that the port reads the same values in both row-wise and col-wise mode. `test_forced_splits_change_trees` checks that every case changes upstream's trees. `test_forced_splits_errors_and_files` compares the error messages and the handling of missing, unparsable and non-object files.
- **Feature-group storage.** `test_storage.py` trains on three sparse datasets whose upstream layouts include exclusive bundles, a multi-value group with a sparse row-wise bin, and sparse single-feature bins in the validation sets. Each runs row-wise and col-wise at 1 and 4 threads, with variants that select the sub-column multi-value bin (`feature_fraction=0.3`), bagging subsets, 4-bit bins (`max_bin=15`) and the `enable_bundle` / `is_enable_sparse` switches. At 1 thread the model text, per-iteration validation metrics and predictions must be exact; at 4 threads the trees must be identical and the values are compared under the `multithread` tolerance. The same datasets are also loaded from CSR, CSC, CSV (with and without `two_round`) and LibSVM input, compared through `_dump_text` (including `num_groups`), round-tripped through binary files, and trained with forced splits on bundled and multi-value features.
- **Quantized gradients (`test_quant.py`).** Regression, binary, Huber and Poisson objectives train with `use_quantized_grad=true` under 13 variants: stochastic rounding on and off, 2 and 16 gradient bins, leaf renewing, bagging with and without a subset, GOSS, regularization, extra trees, sorted and one-hot categorical splits, and basic monotone constraints. Each runs row-wise and col-wise at 1 and 4 threads. A sparse dataset adds bundled, sparse and multi-value groups, and weighted regression and lambdarank cover non-constant hessians with and without renewing. At 1 thread the model text, per-iteration validation metrics and predictions must be exact. At 4 threads the trees must be identical, and the values are compared under the `multithread` tolerance, because upstream sums the root totals and renewed leaf outputs with OpenMP reductions. Poisson with full-data bagging hits upstream's own `right_count > 0` check, because upstream's bagged root sums read the packed integers by bag position. For those 4 cases the test requires lightgbm-rust to raise the same message. `test_quantized_gates` checks the combinations that are rejected as unsupported.
- **Parameter resets and training-set replacement.** The `reset_*` cases change parameters before every round through the `reset_parameter` callback (`test_reset_parameter_schedules`, 4 of them also through `cv`) or call `Booster.reset_parameter` with a new `objective` or `seed` (`test_reset_objective`). The `update_train_set_*` cases continue on a row subset built with `reference=train` (`test_update_train_set`). Datasets built outside `train()` get `num_threads=1`, because upstream's Dataset constructor otherwise resets OpenMP to all cores and its metric sums change order. Schedules that upstream cannot run are not compared: switching bagging or GOSS between subset and full-data mode after a bag, a GOSS warm-up after a subset bag, and raising `num_leaves` with CEGB. In these upstream reads or writes past its buffers and fails a check, crashes or returns garbage. `test_reset_parameter_unsupported` checks that lightgbm-rust raises "not supported" for each of them.
- **First-iteration gradients and Hessians.** These are compared against a NumPy reference that reproduces upstream's float32 arithmetic and summation order.
- **Model and predictions.** The checks cover:
  - the full model text, byte for byte;
  - per-tree arrays (split feature, threshold, gain, default direction, children, leaf values, and counts);
  - predictions (raw, transformed, leaf index, and iteration windows);
  - feature importance and metrics;
  - early stopping;
  - model cross-loading in both directions.
- **Text files (`test_text_files.py`).** Both engines load the same CSV, TSV and LibSVM files (written with side files into a temporary directory) and predict from them; error cases compare upstream's message with ours after removing our `invalid data:` / `invalid parameter:` prefix and upstream's source location in `CHECK` messages.
- **Engine log (`test_logs.py`).** 19 scenarios register a logger in each package and run at `verbosity=2`: bagging, GOSS, multiclass with `auc_mu`, OVA, L1 without `boost_from_average`, `huber` with `reg_sqrt`, both cross-entropy objectives, lambdarank with positions, a tree that cannot split, random forest, a custom objective, a learning-rate schedule, text files with a header and side files (training and validation, `two_round`, prediction from the file), a ranking file and side files without trailing newlines saved and reloaded as binary, sparse data with a multi-value group in row-wise and col-wise mode, and `save_binary`. Every Info, Warning and Debug line must match upstream's in text and order. Only elapsed times (`<elapsed> seconds`) and the temporary directory are replaced before the comparison (`[log]` in `tests/tolerances.toml`).
- **Plotting (`test_plotting.py`).** Each package plots the same regression and multiclass models. The test compares `get_split_value_histogram` results, the graphviz source of `create_tree_digraph`, a description of every matplotlib axes (title, labels, limits, ticks, bars, lines, texts, legend, grid and image pixels, including the trees rendered by `plot_tree`), and the error messages. It runs on matplotlib's `Agg` backend; `test_plot_tree` is skipped without Graphviz's `dot`.
- **Tolerances.** These come from `tests/tolerances.toml`; every entry has a written rationale. A comparison that exceeds its tolerance fails, and no tolerance is widened to make a test pass.
- **Report.** Every comparison, including its max abs/rel diff and whether it was bitwise exact, goes to `tests/report/differential.json`.

### Upstream Python suite (`tests/upstream_runner`)
- **Mechanism.** `shim_plugin.py` aliases `lightgbm`, `lightgbm.basic`, `lightgbm.callback`, `lightgbm.compat`, `lightgbm.engine`, and `lightgbm.sklearn` to the `lightgbm_rust` modules. The upstream test files run unmodified from the submodule.
- **Classification.** Each test is classified as one of:
  - `passed`: the upstream assertions hold.
  - `failed`: any assertion or unexpected error. Each one is a behavioral difference or a bug, and is listed individually in the report.
  - `unsupported`: the test needs a feature that lightgbm-rust reports as not implemented, i.e. it raises `LightGBMError("not supported by lightgbm-rust yet: ...")`. This category also covers tests that need an API that does not exist yet. Missing-API errors are matched narrowly: only `module 'lightgbm…' has no attribute`, a missing attribute on `Booster`/`Dataset`/etc., or an unexpected keyword to one of our functions count. Any other `AttributeError`/`TypeError` is `failed`. Also counted as `unsupported` is a `pytest.raises(match=...)` that received our "not supported" error instead of the expected message, and a failure whose error or an earlier warning in the same test carries the "not supported" message. scikit-learn's model selection reports failed fits that way (a `ValueError` listing their tracebacks, or a `FitFailedWarning` followed by a failed assertion on the scores); the recorded reason names both. Upstream *private* helpers that tests call directly (`_data_from_pandas`, `_np2d_to_np1d`, `Dataset._handle`, ...) fall in this category too.
  - `skipped`: skipped by upstream's own markers or conditions. The reason is kept.
  - `adapted`: listed in `ADAPTATIONS` in `shim_plugin.py`, with a reason. This list is currently empty, because no upstream test has been modified.
- **Collection errors.** A module whose import fails (currently none) is reported with its number of test functions from `docs/compat/upstream_tests.csv`.

## Determinism

Every reduction runs in a fixed order, so repeated runs with the same thread count give identical results.

- **Row-wise histograms (the default).** These are split into blocks by upstream's `Threading::BlockInfo` and merged in block order, like upstream. Results therefore depend on the thread count exactly as upstream's do.
- **Col-wise histograms.** These do not depend on the thread count.
- **Differential checks (`test_multithread`).** These compare 4-thread row-wise training against upstream at 4 threads, and col-wise at 4 threads against 1 thread. All comparisons are exact.
- **Rust checks.** `histogram_layouts_and_thread_counts_agree` checks three things: row-wise and col-wise agree at 1 thread, col-wise does not depend on thread count, and row-wise is reproducible.
- **Benchmark caveat.** The benchmark runs both engines without `deterministic=true`. Upstream then computes `BoostFromScore` with an OpenMP reduction, so its multithreaded regression predictions can differ from ours in the last bits (up to 1.8e-15 observed).
